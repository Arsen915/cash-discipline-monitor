# Кассовый контроль — AI-сервис выявления нарушений кассовой дисциплины по видео

MVP для дататона ForteBank. Сервис принимает видеозапись с камеры над кассой (`.mov`),
находит визуально наблюдаемые признаки возможных нарушений и возвращает вердикт, тип,
таймкод, описание, 1–3 кадра-доказательства (JPEG/base64) и ссылку на пункт норматива НБРК.

**Всё работает локально**: никаких облачных LLM/Vision API. Модель детекции — YOLOX
(Apache-2.0) в ONNX на CPU через onnxruntime; веса скачиваются один раз при сборке,
после этого интернет не нужен (сервис можно перенести во внутренний контур банка).

---

```
│   │   ├── api/routes.py       # POST /api/v1/analyze, GET /api/v1/jobs/{id}, /violation-types
│   │   ├── jobs/               # очередь задач, пул воркеров, хранение результатов на диске
│   │   └── pipeline/

│   │       ├── detector.py     # YOLOX-ONNX (по умолчанию) / Ultralytics (опционально)
│   │       ├── tracker.py      # IoU-трекер людей
│   │       ├── quality.py      # метрики кадра, детекция перекрытия камеры
│   │       ├── zones.py        # зоны кассы: ручные (JSON) или автокалибровка
│   │       ├── scene.py        # кто где находится в каждом кадре
│   │       ├── rules/          # правила нарушений + каталог нормативных оснований
│   │       ├── evidence.py     # кадры-доказательства: аннотация, JPEG, base64
│   │       └── analyzer.py     # оркестрация всего анализа
│   ├── config/                 # примеры zones.json / rules.json
│   ├── scripts/download_models.py   # скачивание весов YOLOX с проверкой SHA-256
│   ├── tools/                  # analyze_file.py, evaluate.py — отладка и подбор порогов
│   └── tests/                  # pytest: правила на синтетическом видео + API
└── frontend/                   # React 18 + Vite 5 + Tailwind 3
    ├── Dockerfile              # сборка → nginx
    ├── nginx.conf              # статика + прокси /api, /docs на backend
    └── src/
        ├── App.jsx             # состояние: загрузка → опрос статуса → результат
        ├── api.js              # клиент API (XHR с прогрессом загрузки, fetch)
        └── components/         # UploadPanel, ProcessingPanel, ResultView, ViolationCard,
                                # Timeline, Lightbox, ApiKeyPanel, ViolationTypes
```

Поток обработки:

```
POST /api/v1/analyze ──► файл на диск ──► очередь ──► воркер (поток)
                                                     │
  1. OpenCV: последовательное декодирование, выборка ~3 кадра/с (адаптивно под бюджет 55 с — анализ укладывается примерно в минуту)
  2. YOLOX: люди, телефоны, сумки на полном кадре + дозум на кассира (мелкие предметы)
  3. IoU-трекинг людей, метрики качества кадра
  4. Перекрытие камеры → кадры помечаются непригодными (не дают ложных «отсутствий»)
  5. Зоны кассы: ZONES_FILE или автокалибровка по траекториям
  6. Правила по временным рядам состояния сцены → события с таймкодами
  7. Склейка событий, порог уверенности, 1–3 аннотированных JPEG на событие
                                                     │
GET /api/v1/jobs/{id} ◄── status: processing / done / failed + результат
```

Задачи сохраняются в `DATA_DIR/jobs/*.json`: после перезапуска сервиса незавершённые
задачи возвращаются в очередь. Видео удаляется сразу после обработки (`KEEP_UPLOADS=false`) —
тестовые видео жюри не хранятся.

## 2. Быстрый старт (Docker)

```bash
cp .env.example .env
```

Задайте в `.env` свой `API_KEY`, затем:

```bash
docker compose up -d --build
```

* UI: `http://<сервер>/` (порт `PUBLIC_PORT`, по умолчанию 80)
* API: `http://<сервер>/api/v1/...`, Swagger: `http://<сервер>/docs`
* Проверка: `curl http://<сервер>/api/health`

Для публичного HTTPS-адреса поставьте перед стеком обратный прокси с TLS (Caddy/Traefik/nginx +
Let's Encrypt) или, для демо, туннель (`cloudflared tunnel --url http://localhost:80`).
Туннель только пересылает трафик — анализ по-прежнему выполняется на вашем сервере.

## 3. Локальный запуск без Docker

```bash
cd backend
python -m venv .venv
.venv/bin/pip install -r requirements-dev.txt      # Windows: .venv\Scripts\pip
.venv/bin/python scripts/download_models.py
API_KEY=dev-key .venv/bin/uvicorn app.main:create_app --factory --port 8000
```

Фронтенд (Node 18+), в другом терминале — dev-сервер проксирует `/api` на `localhost:8000`:

```bash
cd frontend
npm install
npm run dev
```

Вариант «одним процессом»: `npm run build`, затем запустить бэкенд с `STATIC_DIR=../frontend/dist` —
FastAPI сам отдаст UI.

Тесты бэкенда:

```bash
cd backend && .venv/bin/python -m pytest -q
```

## 4. API

```bash
curl -X POST https://team.example.kz/api/v1/analyze -H "X-API-Key: <ключ>" -F "file=@video_017.mov"
# {"job_id":"3f2a9c1e5b7d4a60"}

curl https://team.example.kz/api/v1/jobs/3f2a9c1e5b7d4a60 -H "X-API-Key: <ключ>"
```

## 5. Распознаваемые типы нарушений и нормативная база

Источники — только акты РК с официальной базы «Әділет»:

* **[НБРК-231]** Правила осуществления кассовых операций и операций по инкассации банкнот, монет и ценностей
  в банках второго уровня…, утв. постановлением Правления НБРК от 29.11.2019 № 231 (рег. № 19680) —
  <https://adilet.zan.kz/rus/docs/V1900019680>
* **[НБРК-14]** Правила организации охраны и устройства помещений банков второго уровня…,
  утв. постановлением Правления НБРК от 24.02.2020 № 14 (рег. № 20075) —
  <https://adilet.zan.kz/rus/docs/V2000020075>

### Модель помещения — правила по умолчанию (`RULESET=room`), любой ракурс

Сервис сам находит **рабочее место кассира** — место, где с первой секунды записи дольше всех
непрерывно находится один и тот же человек. Место, на котором сменяются разные люди (стул
клиента), кассиром не считается. Все расстояния меряются в **ростах кассира** (высота его фигуры
в кадре), поэтому одни и те же пороги работают для камеры сверху, под углом и сбоку. Люди за
стеклянной перегородкой и отражения отсеиваются: это треки, которые детектор видит неуверенно
(средняя уверенность < 0.55) и которые ни разу не подходили к рабочему месту кассира.

| Код | Тип | Что видно на видео (логика) | Основание |
|---|---|---|---|
| `WORKPLACE_LEFT_UNSECURED` | Кассир покинул рабочее место, не обеспечив его сохранность | Трек кассира пропадает из помещения (людей становится меньше). Нарушение, если у стола остался клиент или экран компьютера после ухода выглядит так же, как во время работы. Таймкод — момент, когда кассир отошёл от кресла | НБРК-231, п. 22, п. 20 |
| `STORAGE_LEFT_OPEN` | Сейф оставлен открытым | Кассир работал у сейфа/шкафа и отошёл, а вид этого места остался изменённым по сравнению с видом до взаимодействия | НБРК-231, п. 20 |
| `DOOR_LEFT_OPEN` | Дверь кассового помещения оставлена открытой | Человек прошёл через дверь, и после этого дверь выглядит иначе, чем до прохода | НБРК-14, п. 8, пп. 1) п. 16 |
| `MOBILE_PHONE` | Мобильный телефон у кассира | «cell phone» в руках кассира: размер ≥ 0.15 его роста (пачки купюр и калькулятор, которые COCO тоже называет телефоном, мельче), пик уверенности ≥ 0.55, ≥ 3 кадра | НБРК-231, п. 12 (только средства связи без фото-/видеофиксации) |
| `PERSONAL_BELONGINGS` | Личные вещи у рабочего места | Сумка/рюкзак, появившиеся у рабочего места в ходе записи (оборудование, стоящее с начала записи, не учитывается), средняя уверенность ≥ 0.4 | НБРК-231, п. 12 (личные вещи — вне кассового узла) |
| `UNAUTHORIZED_PERSON` | Посторонний в помещении кассы | Одновременно больше двух человек (кассир, клиент и ещё кто-то) ≥ 1.5 с | НБРК-14, п. 8, пп. 1) п. 16 |
| `CAMERA_OBSTRUCTION` | Перекрыт обзор камеры | Кадр однороден/тёмный или большая часть кадра потеряла текстуру ≥ 1.5 с | НБРК-14, пп. 6) п. 16 |

Принцип «до/после» (сейф, дверь, экран): сравнивается вид одного и того же места на кадрах, где
его не заслоняют люди, до и после действия человека; общее изменение яркости (автоэкспозиция)
компенсируется.

### Камера строго сверху над кабиной со стойкой (`RULESET=overhead`)

Набор с зонами «за стойкой / у стойки» (автокалибровка или `ZONES_FILE`):

| Код | Тип | Что видно на видео (логика) | Основание |
|---|---|---|---|
| `WORKPLACE_ABANDONED` | Кассир покинул рабочее место во время обслуживания клиента | Рабочее место пустует ≥ 3 с, а клиент у стойки в момент ухода (или ≥ 60 % времени отсутствия). Таймкод — момент ухода | НБРК-231, п. 22 |
| `WORKPLACE_LEFT` | Кассир отлучился с рабочего места во время смены | Кассир работал на месте, затем рабочее место пустует ≥ 30 с при отсутствии клиента у стойки. Таймкоды — уход и возвращение; если на столе остались предметы, вместо него выдаётся `CASH_UNATTENDED` | НБРК-231, п. 20, п. 22 (пересказ; порядок перерывов — внутренние документы банка) |
| `CASH_UNATTENDED` | Ценности оставлены без присмотра | Кассир отсутствует ≥ 6 с без клиента, а на столе есть предметы, которых нет на «чистом» эталонном кадре стола | НБРК-231, п. 20 |
| `UNAUTHORIZED_PERSON` | Посторонний в зоне кассира | Трек человека из клиентской зоны переходит за стойку на ≥ 2 с; или за стойкой ≥ 2 человек дольше 8 с | НБРК-14, п. 8, пп. 1) п. 16 |
| `MOBILE_PHONE` | Мобильный телефон в зоне кассира | Детекция «cell phone» за стойкой на ≥ 3 кадрах (с дозумом на кассира); телефон в руке кассира — достаточно 2 кадров при пониженном пороге. Неподвижный «телефон» на столе всю запись (денежный терминал) отбрасывается | НБРК-231, п. 12 (только средства связи без фото-/видеофиксации) |
| `PERSONAL_BELONGINGS` | Личные вещи в зоне кассира | Сумка/рюкзак за стойкой ≥ 4 с, не в руках клиента. Не считаются сумкой: объект, совпадающий с оборудованием («tv», «laptop», «microwave» и т. п.), и неподвижный неуверенный «suitcase» на всю запись — так модель видит принтер | НБРК-231, п. 12 (личные вещи — вне кассового узла) |
| `CAMERA_OBSTRUCTION` | Перекрыт обзор камеры | Кадр однороден/тёмный или ≥ 50 % ячеек потеряли текстуру относительно нормального вида ≥ 1.5 с | НБРК-14, пп. 6) п. 16 (касса оборудуется видеокамерами) |

Принцип сопоставления: правило срабатывает только на то, что видно в кадре (люди, предметы,
зоны, время). Каждое описание говорит, *что видно* и *почему это может нарушать* конкретный пункт;
где по кадру нельзя установить факт (есть ли у телефона камера, чья это сумка), это прямо
указано для проверяющего. Выводы о проводках, сверках и прочих невидимых данных не делаются.

## 6. Качество на датасете и калибровка

Пороги модели помещения подобраны на обучающем датасете (42 видео: 22 с нарушением, 20 без;
YOLOX-s, 2.5 кадра/с, дозум на кассира):

| Набор правил | Точность вердикта | Нарушение найдено | Ложные срабатывания | Таймкод ±2.5 с |
|---|---|---|---|---|
| `overhead` (зоны стойки) | 45 % | 17 из 22 | 18 из 20 чистых | 3 из 22 |
| `room` (по умолчанию) | **69 %** | 12 из 22 | **3 из 20 чистых** | 5 из 22 |

Пороги подбирались на тех же 42 видео, отдельной проверочной выборки нет — на новых видео
точность может быть ниже. Пропускаются нарушения, для которых нет надёжного визуального признака
(см. раздел 8): ручной пересчёт купюр при клиенте, клиент уходит до окончания пересчёта, сейф,
открытый с самого начала записи.

```bash
cd backend
# разбор одного видео: result.json, кадры-доказательства, timeline.csv, zones.json
python -m tools.analyze_file dataset/video_001.mov --out out/video_001

# метрики по всему датасету (вердикт, recall/precision, попадание таймкода);
# --cache сохраняет детекции, повторные прогоны с другими --rules занимают секунды
python -m tools.evaluate --videos dataset/ --labels labels.csv --out eval/ --cache cache/
```

`labels.csv`: `file,label,timecode_sec` (одна строка на событие; `no_violation` с пустым таймкодом).

* **Зоны**: если все видео сняты одной камерой, возьмите `out/<видео>/zones.json`, поправьте
  и подключите через `ZONES_FILE` (формат — `backend/config/zones.example.json`). Без файла
  зоны находятся автоматически — это нужно для финального видео под другим углом.
* **Пороги**: скопируйте `backend/config/rules.example.json` в `rules.json`, меняйте значения,
  перепроверяйте `tools.evaluate`, подключайте через `RULES_FILE`. Полный список параметров —
  `backend/app/pipeline/rule_config.py`.
* Приоритет ТЗ — не пропустить нарушение: при сомнениях снижайте `min_confidence` и пороги длительности.

## 7. Производительность

На 8-поточном ноутбучном CPU: YOLOX-tiny ≈ 0.09 с/кадр, YOLOX-s ≈ 0.33–0.45 с/кадр.
По умолчанию — YOLOX-s (пороги подобраны под неё), 2.5 кадра/с, дозум включён, бюджет
`PROCESSING_BUDGET_SEC=120`: ролик 20–30 с обрабатывается примерно за 30–60 с.
Если прогноз превышает бюджет, шаг выборки автоматически увеличивается (до 1.5 с), чтобы анализ
уложился в лимит жюри 5 минут. На слабом CPU можно вернуть `MODEL_FILE=yolox_tiny.onnx`
(быстрее, но хуже видит телефоны в руках).

## 8. Ограничения и известные случаи ошибок

* **Детектор обучен на COCO, правила эвристические.** Пороги подобраны на 42 обучающих видео
  (раздел 6); на видео с другим помещением и освещением точность может быть ниже.
* **Определение кассира**: кассиром считается человек, непрерывно присутствующий на одном месте с
  начала записи. Если запись начинается без кассира, а клиент сидит всю запись, рабочее место
  может определиться по клиенту.
* **Уход с рабочего места**: обеспечил ли кассир рабочее место перед уходом, сервис проверяет по
  экрану компьютера. Если экран с этого ракурса не виден (камера смотрит на крышку ноутбука),
  уход отмечается как требующий проверки (уверенность 0.6) — так возможны ложные срабатывания на
  уходах, когда кассир всё убрал в сейф.
* **COCO путает с телефоном** пачки купюр и калькулятор на столе: правило требует крупный
  предмет в руках кассира, поэтому телефон, наполовину закрытый рукой, может быть пропущен.
* **Сейф/дверь** оцениваются только «до/после» взаимодействия: если сейф открыт уже с начала
  записи, сравнивать не с чем, и нарушение пропускается.
* **Не распознаются** признаки, которых нет в детекциях: ручной пересчёт купюр при клиенте, клиент
  уходит до окончания пересчёта, передача ценностей инкассатору с нарушением процедуры.
* **Автокалибровка зон** (набор `overhead`) считает кассиром человека, дольше всех неподвижно
  присутствующего с начала записи → для стационарной камеры используйте `ZONES_FILE`.
* **Вид сверху**: COCO-детектор хуже находит людей строго сверху; при сильных окклюзиях
  трек кассира рвётся. Пропуски детекции короче 0.75 с сглаживаются.
* **Телефон** сверху мелкий; дозум помогает, но телефон, закрытый рукой, или телефон экраном вниз
  может быть пропущен. Похожие предметы (калькулятор, пульт) иногда принимаются за телефон.
* **Сумки**: инкассаторскую сумку модель не отличает от личной — правило требует длительного
  нахождения за стойкой и не срабатывает на сумку в руках клиента/инкассатора.
* **Ценности без присмотра** определяются по изменению вида стола относительно эталона; без
  кадра «чистого» стола правило не делает вывода. Сами купюры как класс не распознаются.
* **Посторонние**: уполномоченный (контролирующий) работник за стойкой может дать срабатывание
  «толпы» — описание прямо просит это проверить.
* **Не распознаются** (требуют обучения на размеченных действиях): пересчёт денег вне поля
  зрения/не в присутствии клиента, передача ценностей минуя транспортирующее устройство,
  нарушения процедуры приёма сумок от инкассаторов, нарушения «по бездействию».
* Браузер может не воспроизвести `.mov` с кодеком HEVC — тогда в UI доступны кадры-доказательства
  и таймкоды, но не встроенный плеер.
* Распознавание и идентификация лиц не выполняются (запрещено ТЗ).

Развитие: дообучение YOLOX на кадрах датасета с классами «купюры», «пачка», «инкассаторская
сумка», «руки»; лёгкий классификатор действий по клипам вокруг событий; калибровка зон в UI.
